# Preservation and migration strategy

## Current connection: system MySQL on port 3306

On 19 November 2026 the user selected **keep current app records and move to port 3306**. The current connection is `127.0.0.1:3306/smart_gym` on the MySQL80 Windows service. The application was stopped during backup/copy/cutover. All 18 base tables, four views, seven routines and five triggers were copied; every table's row count and canonical SHA-256 content fingerprint matched before the private `.env` was switched. JSON fingerprints compare parsed values with canonical keys/numbers, because dump/restore may change JSON text formatting. The new application account has privileges only on `smart_gym`; its password is private. The supplied system administrator password was not stored. Original tables in `gymmembership_workouttracker` remain unchanged (five members). MongoDB and SQL/Mongo member IDs are unchanged.

The source port-3308 database remains intact for rollback. A full source dump, restore copy, prior connection settings and verification are stored in an ignored `backups/move-to-3306-*` directory. Restore `.env` from its private `app.env.before` and restart the app only if an intentional rollback is needed; writes made after cutover exist on 3306 and must be reconciled before reverting. See [MYSQL_MOVE_RESULTS.json](MYSQL_MOVE_RESULTS.json) for verification without credentials. `db:backup` now exports the target on 3306. The provisioner detects this configured server and skips its old isolated-instance branch. Re-running `db:migrate` checks all existing migration checksums and skips applied migrations without requiring a global server setting change. Future pending routine/trigger migrations still require appropriate DBA configuration under binary logging.

## Historical setup before the move

The original Flask source, SQL scripts, private port-3307 database and root environment file are preserved. The original application account could not create triggers under binary logging, or export routine definitions. The initial additive attempt left `sg_` tables, CHECK constraints, four views and synthetic records in the original database; its `002_advanced.sql` was not marked applied. No legacy table or row was modified. Those additive objects are unused by the final application and are retained for inspection rather than silently dropped.

The final application uses a separate local MySQL 8 instance on port **3308**, database **smart_gym**, data directory `../.local/smartgym-mysql`. MongoDB uses `smart_gym`; the existing MongoDB service is reused. The local MySQL provisioner binds only to 127.0.0.1, generates private app/admin passwords, and enables trusted trigger creation at startup for this development instance. It does not change the system MySQL service or the legacy instance.

Before migrations: run `npm run db:backup`. It uses mysqldump with `--single-transaction --routines --triggers --no-tablespaces`, writes to ignored `backups/`, and fails if any required export permission is missing. Keep backups private because they contain personal records and password hashes. The dedicated app account has rights to this database only. Stop application writes and schema changes while taking or restoring a backup; single-transaction protects InnoDB data consistency but not concurrent DDL.

Run `npm run db:setup` for fail-fast backup → migrations → seed → checks. Migration files are applied once, in order, with SHA-256 checksums in `sg_migrations`. Applied files cannot be edited unnoticed. MySQL DDL implicitly commits: if a migration fails partway, do not mark it applied; inspect the partial objects and restore the pre-migration backup into an isolated database before retrying. The runner checks binary-log settings before starting DDL. Never run Prisma migrate reset, db push --accept-data-loss, or legacy SQL imports against an existing populated database.

For restore verification, create a separate empty database with your DBA account, use the MySQL client's `SOURCE absolute/path/to/backup.sql`, then point a temporary DATABASE_URL at it and run `npm run db:check`. Re-run integration tests in that disposable database with matching synthetic account passwords. Do not restore over the legacy database. This project does not automatically copy legacy personal records or plaintext passwords. If a future import is desired, map IDs explicitly, validate duplicates, reconcile subscription dates/payments, and issue new credentials.

For MongoDB backups, with MongoDB Database Tools installed, use `mongodump --uri="YOUR_URI" --db=smart_gym --out=backups/mongodb-DATE`. Restore into a separate database with `mongorestore --nsFrom="smart_gym.*" --nsTo="smart_gym_restore.*" backups/mongodb-DATE`. MongoDB backup/restore is documented, not claimed tested here. MySQL outbox events can be replayed idempotently, but workout/progress documents must be backed up separately.
